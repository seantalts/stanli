# Why you can trust this

stanli is a reimplementation of the Stan runtime. This page is the
inventory of what is checked, how, and where: every claim names the file
that enforces it, and where CI enforces it, the workflow and step.

Every oracle below is differential. There are two axes.

Against CmdStan: the same model, the same data, the same deterministic
evaluation point, compared value by value. Log density, every gradient
component, every generated-quantities column, and 24,277 generated
single-function cases covering the language surface no real posterior
reaches. The reference values on this axis are produced by running Stan,
and are either checked in or regenerated by a rig; none are typed in
by hand. Sampler
configuration is compared separately, because configuration never enters
a pointwise gradient.

Against stanli itself: the runtime has three engines (op graph, MIR
interpreter, register machine) and eleven graph transformations, each
with its own kill switch, and two of its own dispatch tables can agree on
a wrong reading of one Stan line. There is no external reference on this
axis; the comparison is between live configurations of the same build.
The cross-path matrix compiles one model once per engine configuration
and requires bitwise agreement. The pass A/B compares the optimized graph
against the unoptimized one, which is the graph the CmdStan references
verified.

The standing bar, everywhere: a supported density's gradients match
CmdStan bitwise at the tested points. Where bitwise is impossible the
budget is 2 ULP, and a tolerance may only be chosen after the actual
error has been measured and its mechanism named in a comment. A gradient
that agrees only to 1e-12 is treated as a bug report.

## The corpus oracle

[`tools/verify_refs.py`](tools/verify_refs.py) replays every referenced
posteriordb model, plus the language-construct models in
[`tests/stanc3/`](tests/stanc3/), against CmdStan's recorded log density
and full unconstrained gradient. It is the strongest oracle in the repo
and has caught what unit tests missed: models silently wrong by large
factors have reached main with every test green, and only this diff
flagged them.

What is in [`docs/corpus-refs.json.gz`](docs/corpus-refs.json.gz):

- 129 models at 3 deterministic unconstrained points each, 387 points in
  total, holding 347,920 lp and gradient values.
- Every value is the exact `%.17g` string CmdStan's driver printed
  ([`tools/ref_driver.cpp`](tools/ref_driver.cpp)), so the replay
  compares against the bits CmdStan produced rather than a rounded copy.
- 108 of those models also carry CmdStan's full `write_array` row at the
  same point: 452,754 values covering constrained parameters,
  transformed parameters, and generated quantities, with column names
  compared exactly. Per-model counts are in
  [`docs/corpus-status.md`](docs/corpus-status.md). Models whose
  generated quantities call an RNG carry no values, since those are a
  property of the RNG stream; `--wa-report` reports structural coverage
  for them instead.
- The provenance the values came out of, recorded in the file: CmdStan
  2.39.0 at `11cb052d`, Stan `c96d0411`, Math `8f326d14`, stanc3
  `ac69570a`, posteriordb `28f8d3d6`, on Darwin arm64.

The references were recorded by
[`tools/verify_sample.py`](tools/verify_sample.py) against that CmdStan
checkout, compiled with `-ffp-contract=off` to match CmdStan's own build
flags. stanli sets the same flag on stan-math project-wide
([`CMakeLists.txt`](CMakeLists.txt), line 113). Both sides use
`propto=false` plus the Jacobian, so no dropped-constant difference in
`lp__` is expected either. Every point is recorded, including the points
CmdStan itself refuses, which stanli then has to reproduce. The recorder
used to stop at the first point that worked, which is the opposite of
what an oracle is for.

The replay gate is 1e-9 relative, looser than the 1e-10 the generating
rig holds itself to, because the references were recorded against Apple's
libm and other platforms round transcendentals differently. Every bug
class that has actually reached the corpus (silent in-place corruption at
1.7e+05 relative, quadratic recompute, dropped tape links) sits many
orders of magnitude above that; cross-libm drift sits well below.

Of the 387 points, 381 are recorded `VERIFIED`, 5 `MISMATCH`, and 1
`REJECTED_BOTH`. A `MISMATCH` point is one whose disagreement with
CmdStan is understood and written down. It is not exempt from gating:
`gate_for()` holds it to four times the worst cross-platform measurement
of its own deviation, with a floor, so it cannot get much worse
unnoticed, while a clean point keeps the clean gate. All five are
`kronecker_gp`, whose two eigenvector gradients are amplified by a
covariance with eigenvalue gaps down to 6.5e-17. The separate escape
hatch, `QUARANTINED`, is empty. An entry there requires naming the live
CmdStan run that settled it, and deleting the entry restores full
three-point parity.

In CI: the step "Corpus verification against CmdStan references" in
[`.github/workflows/wheels.yml`](.github/workflows/wheels.yml), on every
pull request, every push to `main`, and nightly.
[`tools/wasm_check.sh`](tools/wasm_check.sh) drives the same replay
through the WebAssembly build, where 118 of the 119 compiling corpus
models pass. `nn_rbm1bJ100` is the exception: its compile does not fit in
wasm32's 4 GB.

What this layer cannot see: language surface no real posterior uses,
which is most of it. The conformance sweep exists for that.

## What bitwise means here

[`docs/corpus-status.md`](docs/corpus-status.md) publishes the worst
deviation per model in both relative terms and ULPs. 41 of the verified
models come out at 0 ULP: every lp and every gradient component
bit-identical to CmdStan.

The mechanism is that the two sides run the same arithmetic. stanli calls
the same stan-math library CmdStan calls, compiled with the same
floating-point flags, and its native kernels transcribe stan-math's own
reverse-mode expressions rather than rederiving them. Where a kernel
sums, it sums in the direction the reference sums, because floating-point
addition is not associative and `(a+b)+c` can differ from `a+(b+c)` in
the last bit. The kernel contract in
[`docs/hacking.md`](docs/hacking.md) records the trap: a reordered sum
still passes the corpus check at 1e-9 and fails
[`tests/test_matvec.cpp`](tests/test_matvec.cpp) at 1 ULP.

Where bitwise is given up it is given up deliberately and recorded at the
call site. The elementwise `log` kernel takes Eigen's packet path, which
is a ulp off libm on some arguments; the matching packet `exp` is not
taken, because it puts `kronecker_gp` over its reference gate
([`runtime/kernels/eltwise_expr.cpp`](runtime/kernels/eltwise_expr.cpp),
line 333). Several reassociating Eigen paths cost 1-2 ULP and say so
where they are used.

## Unit and kernel tests

The ctest suite pins kernels against stan-math itself: the test
constructs the same call CmdStan's generated C++ would make, on
`stan::math::var`, and compares value plus every gradient, bitwise by
default (`expect_eq`). There are 53 C++ test binaries, roughly one per
subsystem, listed as `STANLI_TESTS` in
[`CMakeLists.txt`](CMakeLists.txt), plus `test_capi`, which is linked
against the shipped shared library so the C ABI is tested through the
boundary users load.

Two practices are house style rather than suggestion:

- RED first. A fix's test is verified to fail against the pre-fix source
  (stash the runtime change, rebuild, watch it fail for the right reason)
  before the fix counts. A test that was never red proves nothing about
  the bug it claims to pin.
- Reference activity is chosen on purpose. A same-activity var reference
  gives a bitwise pin; CmdStan's mixed data/var instantiation
  reassociates and lands tens of ULP away. Tests say which they use and
  why, and never split the difference with a loose tolerance.

Two tests in the suite check properties rather than results.

[`tests/test_pass_safety.cpp`](tests/test_pass_safety.cpp) checks the
`backward_ignores_values` allowlist, which is what permits a destructive
write before an op's backward runs. Every opcode on the list is checked
by poisoning all input and output value buffers with NaN between the
forward and backward sweeps, so an op that reads values there produces
NaN adjoints and fails. The same file then runs 400 randomly generated
graphs, built from the shapes real models produce, through every pass and
compares gradients before and after.

[`tests/graph_helpers.hpp`](tests/graph_helpers.hpp)'s `run_grad`
evaluates every pass test twice on the same executor and aborts on any
bit difference. That pins a class this project shipped once: constant
folding turned a `rep_vector` base into a bind-time fill, the in-place
element writes then accumulated across evaluations, and the same point
evaluated four times gave four different log densities. The refusal that
now prevents it is in
[`runtime/src/constfold.cpp`](runtime/src/constfold.cpp), with the
mechanism written out there. Nothing structural showed the bug, and no
other gate in the project could see it: they all evaluate once per
process.

Fixture MIR is generated from checked-in .stan files with the pinned
compiler: `./deps/stanc3/stanc --O1 --debug-optimized-mir tests/fixtures/X.stan
> tests/fixtures/X.tmir.sexp` (then delete the `.hpp` stanc drops next to
it).

What this layer cannot see: a whole execution path computing something
else. A kernel test exercises the kernel you thought to write it for.

## stanli against itself

The CmdStan axis is blind to stanli agreeing with CmdStan on the path the
corpus happens to take while a second path inside stanli answers
differently. The graph lowering, the MIR interpreter, and the register
program each carry their own name-to-operation table, and matrix division
was once `mir_interp.hpp` knowing a rule `lower.cpp` lacked.

[`tests/cross_path.hpp`](tests/cross_path.hpp) compiles one model several
times, once per configuration, and differences the answers. The
configurations are `STANLI_NO_ISLAND`, `STANLI_ISLAND_ALWAYS`,
`STANLI_NO_NATIVE_ADJ`, all passes off, and the shipped pipeline with
`STANLI_WA_FORCE_INTERP` attaching `WaInterp` beside a complete
write_array graph so both engines produce the same CSV row.

The gate is bitwise for every row. A divergence fails unless
[`tests/cross_path_ledger.json`](tests/cross_path_ledger.json) declares
it, with a bound and a cause naming the mechanism. That is not a
tolerance, so a new 1 ULP drift stays visible instead of being absorbed
by a budget. Four entries are in the ledger today. Three are vocabulary
gaps where the interpreter refuses a function the write_array graph
lowers (`dirichlet_lpdf`, `ode_rk45`, `to_matrix`), leaving those
sections with one implementation and no cross-check. The fourth is
recorded as "OPEN BUG, and the GRAPH is the wrong side": on
`array[0] matrix[2, 3]` the interpreter throws where the graph answers.

[`tests/test_cross_path.cpp`](tests/test_cross_path.cpp) drives the
matrix over every `tests/fixtures/*.tmir.sexp` (137 today), so a new
feature's own fixture becomes a cross-check input the day it lands.
Fixtures that cannot compile or cannot evaluate are recorded as skipped,
and measured floors keep the skip list from swallowing a regression: at
least 85 fixtures must drive the matrix, at least 9 must reach an island,
at least 7 a necessity island, at least 2 a carved island, at least 2 a
generated adjoint, at least 1 the ODE integrator, at least 80 must lower
their whole write_array section, and at least 800 write_array columns
must be differenced against the interpreter.

Islands have their own oracle. `gen_adjoint`
([`runtime/src/adjoint.cpp`](runtime/src/adjoint.cpp)) generates an
island's backward as a second instruction list at load time;
`STANLI_NO_NATIVE_ADJ=1` restores the replay under stan-math's `var`,
which is what [`tests/test_adjoint.cpp`](tests/test_adjoint.cpp) checks
the generated program against.

## The passes and their kill switches

Every graph transformation has an environment switch that turns it off:
`STANLI_NO_DATA_PRELOAD`, `STANLI_NO_INPLACE`, `STANLI_NO_CONSTFOLD`,
`STANLI_NO_CSE`, `STANLI_NO_REROLL`, `STANLI_NO_PARTITION`,
`STANLI_NO_ISLAND`, `STANLI_NO_ISLAND_COMPACT`, `STANLI_NO_DENSITY_MASK`,
`STANLI_NO_NATIVE_ADJ`, plus `STANLI_ISLAND_ALWAYS` to carve past the
cost model. They exist so a wrong result can be attributed to one pass in
one run, and they are how every speed number is measured: the same build
with one variable set and unset.
[`runtime/src/OPTIMIZATIONS.md`](runtime/src/OPTIMIZATIONS.md) documents
each pass and its switch.

[`harnesses/ab_corpus.py`](harnesses/ab_corpus.py) evaluates every
posteriordb model with the passes disabled and enabled and compares the
log density and every gradient component. The passes-off graph is the
graph the CmdStan references verified, so A/B parity is transitive
verification of the optimized graph. It has caught bugs the unit tests
missed, including eight models silently wrong by up to 1.7e+05 relative
with their op counts unchanged.

Landing a pass is held to that. The 0.9.1 compatibility note in
[`CHANGELOG.md`](CHANGELOG.md) records the pass stack replaying the full
CmdStan reference corpus with its worst line unmoved, and the worst
deviation any of those passes introduces against the untransformed graph
measured at 5.99e-13.

## The conformance sweep

[`harnesses/stan_conformance.py`](harnesses/stan_conformance.py)
inventories every signature the pinned stanc knows
(`--dump-stan-math-signatures`) plus a catalog of named language
constructs, generates a type-directed model for each case, and evaluates
both sides: stanli, and reference BridgeStan built from the identical
pinned CmdStan/Stan/Math source with the identical source-built stanc,
compiled from the same `--O1` MIR stanli reads. Comparison is lp plus the
complete gradient at deterministic probe points, default gate 10 ULP,
with reviewed exceptions in `harnesses/conformance/policy.toml`. Each
rule carries a mandatory reason naming its mechanism, and stale rules
flag the run.

The checked-in inventory
([`docs/conformance-baseline.json.gz`](docs/conformance-baseline.json.gz))
holds 24,277 cases over 564 function names: 24,246 signatures and 31
language constructs. 18,750 verified, 3,662 inapplicable, 883
`generator_gap`, 695 `expected_unsupported`, 287
`unexpected_unsupported`.

Disagreement blocks a run; absence does not. Blocking statuses: `mismatch` (stanli
answered, differently), `crashed` (the runtime process died, and a
segfault is not a coverage gap), and `harness_error` (the rig itself
failed). The list is `BLOCKING_STATUSES` in
[`harnesses/conformance/status.py`](harnesses/conformance/status.py). A
function stanli has not implemented yet is reported, counted, and given a
reproducer, and does not fail CI. That framing is deliberate: this
runtime is built out from the ground up, and a gate that is red for
"there is still work to do" is a gate nobody reads.

It runs nightly in eight partitions from
[`.github/workflows/stan-conformance-nightly.yml`](.github/workflows/stan-conformance-nightly.yml),
with an aggregate job that rejects missing or duplicate rows before
applying the ratchet. Run it locally (macOS works; only the nightly
*workflow* is Linux):

```sh
tools/dev_setup.sh --conformance          # one-time setup, idempotent
.venv-conformance/bin/python harnesses/stan_conformance.py \
  --stanc deps/stanc3/stanc-pinned --cmdstan deps/cmdstan \
  --build build-rel --stanli-pythonpath python \
  --filter beta_binomial --output /tmp/conf
```

The driver must run under the venv interpreter (TOML support), a filtered
run reporting `partial_run` is expected, and the staged library in
`python/stanli/_bin/` must be re-copied after every rebuild or you are
testing a stale runtime.
[`harnesses/conformance/README.md`](harnesses/conformance/README.md) has
the rest.

What this layer cannot see: behavior reached through operators rather
than function calls (`B / A` silently meaning elementwise division was
never a red row, before or after its fix), anything the generator cannot
build a case for (`generator_gap`), and cost. Conformance asks "same
answer"; the price is out of its scope.

## The coverage ratchet

Relaxing the gate to ignore coverage gaps opened a hole: a regression
that turns a verified function into a compile refusal lands in the
non-blocking bucket, and a green run would not mention the loss. The
nightly therefore compares every classification against
`docs/conformance-baseline.json.gz`, directionally. A case that verified
and no longer does blocks (`coverage_regressed:N`, IDs listed). A
vanished case blocks. A moved toolchain pin blocks, because it
invalidates the comparison. Improvements are recorded and stay green:
wiring a function up must not turn CI red, or the baseline gets
re-stamped on reflex until nobody reads it.

Advancing the baseline is a reviewed act: rerun with `--update-snapshot`
and commit the result in the same PR as the work that earned it.

## The census ratchet

The same idea over whole models rather than signatures. It exists because
the sweep's version could not have caught what broke. #145 turned
`size()` of a scalar `int` into a compile refusal. The corpus uses no
model of that shape; the sweep's generator emits no such case, so its
ratchet had nothing to watch; and the census, which did see it, only
moved a number in a table (392 lowered became 391) with no memory to
compare it to. It took days and somebody refusing to shrug off the tally
to find. Fixed as #151.

So [`harnesses/model_census.py`](harnesses/model_census.py) holds every
run to `docs/census-baseline.json.gz`, per model and on by default, over
stanc3's 1,231 integration models. Two ladders, both directional:

- what the census decided: `lowered` above the six-way backlog
  (`unsupported`, `data_rejected`, ...) above `crashed`/`timed_out`/
  `harness_error`. A model leaving `lowered` blocks by name and prints
  its repro command. A lateral move inside the backlog does not: the line
  between those buckets is a heuristic, and gating it would fire on
  tuning the heuristic.
- what CmdStan said about the models that lowered: `verified` above
  `rejected_both` above disagreement. Consulted only when both runs
  reached a verdict, so a census without `--differential` still ratchets
  on the first ladder rather than reading 382 absent verdicts as 382
  regressions.

A model whose own sha256 moved is void rather than regressed: the
stanc3-src pin advanced and the recorded verdict describes a file that no
longer exists. A model whose *data* sha moved still gates, annotated. The
invented data is redrawn on every generation and cached under the model's
sha, so a changed data sha means a lost cache, and voiding on it would
disarm all 1,231 rows on any cold checkout.

`crashed` and `timed_out` fail the run with or without a baseline; the
ratchet adds direction rather than a level. Advancing it is the same reviewed
act: rerun with `--update-baseline` and commit the file with the work.

## Sampler configuration

Every layer above compares numbers at fixed points. None of them can see
how the sampler is configured, because configuration never enters a
pointwise gradient. That blind spot shipped a bug: `run_nuts` never
called `set_max_depth`, so trajectories capped at 31 leapfrogs instead of
1023, every model needing deep trees was silently under-explored, and
every gradient still verified.

[`tools/sampler_trace.py`](tools/sampler_trace.py) is the oracle for that
class. Same model, same data, same seed, same warmup and sample counts;
compare the distributions of the sampler columns CmdStan writes.
Trajectories diverge between engines after the first accepted proposal
because the RNG streams differ, so the comparison is distributional
rather than pointwise: total leapfrogs, mean and max tree depth, adapted
stepsize, divergence rate, and the `lp__` distribution. The tolerances
are wide on purpose. The target is a 30x leapfrog gap or an
order-of-magnitude stepsize gap, far past Monte Carlo noise.

The executor counts gradient evaluations (`n_grad_evals()`) and
`stanli_run` prints the total, so a sampling-time comparison can be split
into cost per gradient and how many gradients the sampler asked for.
Those are different claims and can move in opposite directions.
[`tests/test_sampling.cpp`](tests/test_sampling.cpp) uses the same
counter to pin the max-depth fix: `ar1` must average more than 40
leapfrogs per iteration, which is impossible under the depth-5 ceiling of
31.

## Memory safety

The memory bugs that reach this project answer with wrong numbers rather
than a crash. A GLM outcome mapping `rows` integers out of a
three-integer group returned -29.48 where the array form gives -16.22,
with no diagnostic, and every test and every corpus model stayed green.
Rebuilt under AddressSanitizer, that configuration reports it on contact:
READ of size 4, zero bytes after a 12-byte region, out of
`poisson_log_glm_lpmf`.

The `asan` job in
[`.github/workflows/wheels.yml`](.github/workflows/wheels.yml) runs the
whole ctest suite with the shadow map on. It runs post-merge and nightly,
not on pull requests: a cold build runs close to its 90-minute ceiling,
which is too long to gate merges on. Locally it is one flag:

```sh
cmake -B build-asan -DCMAKE_BUILD_TYPE=RelWithDebInfo -DSTANLI_SANITIZE=address
cmake --build build-asan -j8 && ctest --test-dir build-asan
```

`address,undefined` also passes clean. What ASan cannot see is a stale
`var`: stan-math's arena recovers a nested tape by rewinding a bump
pointer, so reading a `vari` from a tape that was already recovered lands
inside a live allocation and reports nothing.

## Numeric standards, in one place

- Bitwise wherever the two sides share arithmetic. The default.
- 2 ULP is the outer budget for a var-path comparison, used only with the
  divergence mechanism named in a comment (adjoint contributions summed
  on a fresh tape per op associate differently than on one tape, for
  instance).
- Policy gates in `policy.toml` are for cross-implementation differences
  with an identified cause. Probe sums that cancel toward zero take an
  `abs_tol`, because ULP and relative error describe the cancellation
  rather than the disagreement.
- A tolerance chosen before the error was measured is a defect. One was
  once written as 1e-13 with a plausible rationale; the measured error
  was exactly zero.

## Coverage: what is supported, and how we know

Support is never inferred from stanli's own dispatch tables. A function
listed in a table no path can reach has twice been "supported" that way.
A name counts as covered when the conformance sweep reports no
`unexpected_unsupported` row for it anywhere in the signature space.

Every case carries exactly one status: `verified`, `mismatch`, `crashed`,
`harness_error`, `unexpected_unsupported` (the to-do list),
`expected_unsupported` (a reviewed policy boundary such as complex types
or tuple results, and no entry may be created by observing a
refusal), `generator_gap`
(the harness cannot build the case), or `inapplicable` (nothing real to
test). Every red row has a copy-pasteable repro command, and
`unsupported.md` in each run's output groups the backlog by function.

The human-facing table in [`docs/coverage.md`](docs/coverage.md)
regenerates from a nightly aggregate with the snippet embedded in that
file; drift between the table and the sweep is a bug in the table. A
separate nightly job (`signature-watch`) diffs the pinned signature dump
against stanc3 upstream, so new language surface is reported the day it
appears. Adopting it is a pin advance that re-inventories everything.

## What is gated, and what is only watched

`main` is protected and work lands by pull request. What a pull request
must pass, from
[`.github/workflows/wheels.yml`](.github/workflows/wheels.yml) and
[`.github/workflows/lint.yml`](.github/workflows/lint.yml):

- one platform build, `manylinux_2_28_x86_64`;
- the full ctest suite, which includes the cross-path matrix and the
  pass-safety fuzz;
- the corpus oracle at all three points;
- `tools/gen_docs.py --check`;
- `tools/gen_web_models.py --check`, which requires every demo model to
  carry a hand-written description;
- the manylinux tag check: the highest `GLIBC_*` symbol the library
  imports must be at or below `GLIBC_2.28`, and no dynamic `libstdc++`
  may have leaked in;
- the wheel build, then `tests/test_python.py` and
  `tests/test_bridgestan_embed.py` against the installed wheel in a clean
  venv;
- [`tools/bs_conformance.py`](tools/bs_conformance.py) against reference
  BridgeStan on four fixtures, which is the one check a second
  implementation makes and stanli's own tests cannot, since the facade
  and its tests come from the same head and can agree on a wrong reading
  of what a `bs_` call means;
- the R package's tests under `R CMD check` against the library that
  build produced, with a skipped test treated as a failure;
- `clang-format` over every tracked C/C++ file, pinned to one
  clang-format version because output drifts across major versions.

The pull-request matrix is one platform on purpose, and the workflow
records the measurement: on identical work the arm64 runner took 49.8
minutes against the container's 30.1. The other three wheel platforms
(macOS arm64, macOS x86_64, manylinux aarch64), the Windows build, the
ASan job, the WebAssembly build with its eight-schools sampling test
under Node, and the webR side-module load test all run on every push to
`main`, nightly, and on release tags, where a break is fixed forward
rather than blocking a merge.

Monitored rather than gated: the nightly conformance sweep and its
ratchet, the signature watch, and the model census, which is run by hand.
A ratchet records that coverage has not gone backwards. It says nothing
about how much coverage there is.

Release tags additionally assert that the version in
`python/stanli/__init__.py`, `js/package.json` and `r/R/install.R` agrees
with the tag, that six runtime tarballs exist, and that the PyPI long
description renders.

One gate exists so the prose cannot drift from the measurements. Every
headline number in `README.md`, `python/README.md` and the demo page is
stamped from `docs/verification.json` and `docs/benchmarks.md` by
[`tools/gen_docs.py`](tools/gen_docs.py), and `--check` fails CI when a
stamped number disagrees with its artifact.

## Known limits

Two of the 120 posteriordb corpus models are not differentially verified.
`sir`'s ODE solution dips about 1e-9 below a declared lower bound at
every shared evaluation point and CmdStan rejects it there too, so there
is nothing to compare; that is agreement, and it is not counted as
verification. `kronecker_gp` matches lp to 1e-13 and 436 of 438
gradients, and differs by 0.7% on the two that flow through
`eigenvectors_sym` of a nearly degenerate covariance. Both are written up
in [`docs/corpus-status.md`](docs/corpus-status.md).

Transformed data has one engine. Every cross-path configuration shares
the MIR interpreter's answer there, so that section has no
stanli-internal cross-check and is covered only on the CmdStan axis.
Closing it needs a second path built by derivation rather than forced by
a flag.

Reduction order is not frozen across releases. Fusion and packet
arithmetic change the order of some reductions, so gradients can differ
from an earlier release in their last bits. Releases that do this carry a
compatibility note in [`CHANGELOG.md`](CHANGELOG.md) with the worst
measured deviation against the untransformed graph, and the kill switches
restore the previous graph when a difference needs attributing.

A small number of ULP relaxations are deliberate, each recorded at the
call site: the packet `log` path, and several reassociating Eigen
expressions at 1-2 ULP.

`lp__` is not bitwise for the multivariate and multinomial tail. Those
densities are built the compact way, one instantiation instead of `2^N`,
so `lp__` comes out a per-model constant higher while every gradient
stays exact. See
[`docs/compact-densities.md`](docs/compact-densities.md). The
`STANLI_LITE_LP` build makes the same trade across the whole density
library; it is off by default in every shipped build, browser included,
so any run can be compared against CmdStan directly, and
`stanli_exact_lp()` reports which build is loaded
([`docs/lite-lp.md`](docs/lite-lp.md)).

The conformance backlog is 287 `unexpected_unsupported` cases, each with
a reproducer. Those are functions stanli has not implemented, and they do
not block a run.

The cross-path ledger has four open entries, described above, one of
which is an open bug in the graph.

The `STANLI_LITE_LP` build is not covered by CI, because covering it
would mean a second full stan-math compile. It is checked by hand with
`tools/verify_lite.py`.

## Practices that exist because something went wrong

- Verify a merge landed the commits you think it did; a follow-up commit
  orphaned during a merge left a README pointing at an artifact nothing
  produced.
- A green nightly covers only the commit it was dispatched against,
  and says nothing about merges since; check the run's head SHA before
  citing it.
- A crash at one evaluation point can hide behind success at another. The
  corpus recorder once selected the working point automatically, which is
  the opposite of what an oracle is for.
- Numbers nothing recomputes are numbers that drift. The binary-size
  table and the coverage table both rotted this way; both are generated
  now, and `gen_docs.py --check` fails CI when the stamped numbers
  disagree with their artifacts.
- A state leak is invisible to a rig that evaluates once per process.
  Every pass test now evaluates twice and compares bits.
- Any change that claims a safety property comes with a mutation test:
  break the guard on purpose, watch the test fail, put the guard back. If
  the test still passes with the guard broken, the test is not testing
  the guard.
- Recording references to make a diff go away defeats the oracle, so
  recording is a reviewed act, as is advancing either ratchet baseline.

## Reproducing this locally

The corpus oracle needs no CmdStan and no C++ toolchain beyond the one
that builds stanli, because the references are checked in:

```sh
./tools/dev_setup.sh --corpus     # build, plus posteriordb and the rig
python3 tools/verify_refs.py deps/posteriordb \
  --check build-rel/stanli_check --jobs 8
(cd build-rel && ctest -j4)
```

The rest:

```sh
./tools/dev_setup.sh --conformance   # the reference stack for the sweep
python3 harnesses/ab_corpus.py deps/posteriordb            # pass A/B
build-rel/stanli_check model.stan data.json --cross        # cross-path
python3 tools/verify_refs.py deps/posteriordb --wa-report  # GQ coverage
python3 tools/verify_refs.py deps/posteriordb --wa-headers deps/cmdstan
tools/sampler_trace.py deps/cmdstan deps/posteriordb eight_schools_noncentered
tools/wasm_check.sh                                        # from wasm32
```

`./tools/dev_setup.sh --all` sets up all of it at once.
[`docs/hacking.md`](docs/hacking.md) has the per-change recipes.
[`docs/how-it-works.md`](docs/how-it-works.md) describes the design the
numbers above are checking.
