# Lane layout unification for reroll and partition

The review is right: `reroll.cpp`'s row lanes (d7682c7a, 87ba706f, 1961e33b, cdb756bc) encode one concrete storage shape (a row of an invariant base, covering it exactly) instead of a general affine lane description, and `partition.cpp` already has most of the general machinery. This note specifies a shared description, checks it against the actual graphs lowering produces for the three named gaps, and orders the migration.

An independent static review found five places where this note's first draft was wrong or incomplete about the code, listed under "Amendments after review" below section 4. Read that section alongside sections 2 and 3: it corrects the affine-only claim, the partial-row example, two mischaracterized citations, and the migration order, and is authoritative wherever it disagrees with the surrounding prose left as originally written for context.

## 1. What each pass represents today

| Concept | reroll | partition |
|---|---|---|
| Per-lane operand kind | `PosIn{InKind}` reroll.cpp:62-69: invariant, const-lanes (width `C`), lane-local | `PosIn{InKind}` partition.cpp:136-142: same three, no separate width field (width lives on `Pos`) |
| Whole-region layout | `enum Layout{kAny,kRows,kCols}` reroll.cpp:72, chosen once per region by `adopt_layout` (reroll.cpp:829-835) and read by `flat_at` (reroll.cpp:1331-1333) | none; every wide read is materialized through an explicit per-element index list, so no global row/column choice is needed |
| Row read (base slot varies by row) | `is_row_read`/`row_idata_varies` (reroll.cpp:97-100, 1156-1180): only `OP_SLICE`/`OP_SLICE_STRIDED`, requires `Luse == rows` and `blen == rows*w` (row 0 at offset 0, every row covered) | `indexed_read` (partition.cpp:731-764): any `OP_INDEX`/`OP_SLICE`/`OP_SLICE_STRIDED`, any start, any width; contiguity across the L lanes decides `kElide`/`kSlice`/`kGather` |
| Slice vs. gather | elides to the base or refuses; no explicit slice-of-a-subrange form for a row | picks based on `run` (partition.cpp:751), but **requires `w == 1`** for both `kElide` and `kSlice` (partition.cpp:756,758); a wide contiguous block still gathers |
| Const lane, width > 1 | packs into the base's storage order (`packed_const`, reroll.cpp:1334-1343) | `InKind::kConstLanes` values are always width 1 (partition.cpp:699-716); no wide-constant path |
| Invariant operand, width > 1 | `row_operands_ok` (reroll.cpp:836-861) rejects any invariant input with `len != 1` | same rejection, `wide_shared` (partition.cpp:680,696,812-815) |
| Row store / element store | `Pos::{store_vec,store_src,row_store,store_start,store_stride}` (reroll.cpp:79-93): a per-lane store of `width` elements (a whole row) collapses to one write | `Emit::kStore` (partition.cpp:154, decided at partition.cpp:767-805): a per-lane store of exactly one element (Survey_model's accumulator) collapses to one slice store; not the same op as reroll's row store, which partition does not have a case for |
| Density feeding the target | `term_density`, width may be `> 1` (row_outcomes gate, reroll.cpp:1218-1238) | `Emit::kTermDensity`, `ap.rows` generalizes width for any density (partition.cpp:834-848,1021-1025) |
| Density feeding an expression | `elt_density`, **width fixed at 1**: rejected whenever `ap.width > 1` regardless of cause (reroll.cpp:1218-1222) | `Emit::kEltDensity` with `ap.rows > 1`, tailed by `OP_SUM_ROWS` (partition.cpp:1015-1047); already proven by `test_binomial_elt_fusion` |
| Cost model | none; any classifiable region fuses | explicit, currencies from island.cpp (partition.cpp:50-63, 894-937) |

Three real disagreements, not just naming. Coverage: reroll's row read must start at row 0 and cover the whole base; partition's can start anywhere and be any width, but only `w == 1` gets the cheap `kSlice`/`kElide` form, so a wide contiguous block (reroll's actual common case, a matrix row) still gathers in partition. Neither pass slices a wide, partial, or offset contiguous block; this is the generality note's (2026-09-09-vectorize-consumption-generality.md) item 4, "partition's cost model assumes packing needs a gather." Wide invariant operands: both passes reject a wide invariant operand mixed with lane-varying ones for the identical reason (the vector kernels broadcast length-1 only, and partition hoists the all-shared case first, partition.cpp:807, so the rejection at 812-815 only ever fires on a mixed region, same scope as reroll's `row_operands_ok`); this is a shared gap, not a reroll-specific one. Row-wide density feeding an expression: partition can do it (`kEltDensity` + `SUM_ROWS`); reroll cannot represent it at all, no per-lane-reduction tail exists in `Pos`, so this is not just a missing permission check.

## 2. The shared description

```cpp
struct LaneLayout {
  int base = -1;            // -1: a fresh/computed value, not a base read
  int64_t offset = 0;       // flat position of lane 0, element 0
  int64_t lane_stride = 0;  // flat advance from lane l to l+1
  int64_t elem_stride = 1;  // flat advance from element k to k+1 in a lane
  int64_t width = 1;        // elements per lane (C)
  int64_t count = 1;        // lanes (L)
  bool invariant = false;   // lane_stride == 0: same value every lane
};
```

One `LaneLayout` per operand position, replacing `PosIn` in both passes. It needs two strides, not the one the review's phrasing suggests: today's `Layout::kRows` (row-major: `elem_stride=1`, `lane_stride=C`) and `Layout::kCols` (column-major, dogs' `p[j,:]`: `elem_stride=rows`, `lane_stride=1`) are both real and load-bearing, and one stride would silently refuse one of them. At `width == 1` the two degenerate to the single stride the review names.

A lane-varying row read sets `base` and both strides. A lane-invariant vector (the shared-mean gap) is `lane_stride=0`, `width=C`, `invariant=true`; packing tiles it rather than gathering it (below). A per-lane scalar constant is `width=1` with its values carried alongside the layout, not in it (a `LaneLayout` describes positions, not values, so `CONST_LANES`' data stays a parallel array as today). An advancing element index (`OP_INDEX`, `idata[l] == idata[0] + l`) is `width=1`, `lane_stride=1`. A partial row (`m[i, 2:K]`) is a full row's `base`/strides with `width` less than the native row width and `offset` shifted past the skipped columns: nothing about partiality is special, the "covers the whole base" check is one materialization outcome (elision) a partial row does not qualify for, not part of the type.

**Slice vs. gather** becomes one decision from the layout instead of once per pass: **elide** when `offset == 0`, `count*width` equals the base's length, and the strides match row-major or column-major storage exactly; **slice** when `elem_stride == 1 && lane_stride == width` (one contiguous run, whether or not it covers the whole base); **gather** otherwise. This folds the review's two-way phrasing ("contiguous stride equals width means a slice view, otherwise a gather") by treating elision as the special case of a slice that is the whole base and needs no op. A partial row is a gather under either storage order, since its `lane_stride` (the native row width) never equals its `width` (the truncated one); that is one answer instead of reroll saying "not ours" and partition saying "gather, priced at `2*L*W`."

**Packing** is one op over the concatenation of `count` windows of `width` elements, per the materialization: nothing for elide, one `OP_SLICE`/`OP_SLICE_STRIDED` for slice, one `OP_GATHER` with a flattened index list for gather. A lane-invariant wide operand packs by **tiling**, not gathering: `OP_REP_MAT` already has both forms, selected by its existing mode idata (`rep_matrix`'s row/column-vector cases, lower_funapp.cpp:1774-1802; kernel at elementwise.cpp:346-365): idata `{width, count, 1}` concatenates the operand end to end, row-major (`rep_mat_fwd`'s `out[j*width+i] = v[i]`); idata `{count, width, 2}` repeats each element `count` times consecutively, column-major (`out[j*count+i] = v[j]`). No new opcode, but `rep_mat_bwd` accumulates each source element's adjoint by walking the *output* in ascending flat order (elementwise.cpp:359-364), so this changes the summation order a shared operand's gradient sees; see the amendment on numerical gates before this ships. A density over the packed operands is one call over `count*width` elements: when every lane's result is a term the vector kernel's own sum suffices (today's `term_density`); when a lane's result feeds another op, the call runs elementwise (variant bit 6) over `count*width` outputs, followed by one `OP_SUM_ROWS(width)` folding each lane's `width` elements back to its log-density (`sum_rows_fwd`, mixture.cpp:78-89, reads contiguous `r*width+k` cells), the same `count`-length vector `elt_density` already produces at `width == 1`. This is only sound when the packed operand's flat order actually groups each lane's `width` elements contiguously; see the amendment on source versus pack layout. Everything downstream (log_mix widening, `OP_SUM_VEC`) needs no change.

## 3. The three gaps, checked against real lowering

Dumped with `build-b/stanli_check` at `log_prob:reroll` (`tests/lit/run.py --discover`), not guessed.

**Partial row.** `m` a parameter matrix (data-only `m` folds to constants before reroll sees it and hides the gap):

```stan
parameters { matrix[N, K] m; real mu; real<lower=0> s; }
model { for (i in 1:N) m[i, 2:K] ~ normal(mu, s); }
```

Today (N=8, K=5): lowering already emits one `OP_GATHER` + one `OP_NORMAL_LPDF` per row (17 ops), because a partial row is not one of `lower_stmt.cpp`'s recognized row spellings (the generality note's item 1) and falls to a plain gather over that one row's four elements at flat offsets `{row+8, row+16, row+24, row+32}` (column-major: row `i`, columns 1-4 zero-indexed, land `N=8` apart). reroll's `ops_match` requires identical `idata` for any op that is not `OP_INDEX`/`is_row_read`, so the eight per-lane gathers (different offsets each) do not even count as the same template; the region is invisible before classification runs. See the amendment correcting what this packs to: concatenated in the *base's own storage order* rather than lane-major, the flat span for every row's columns 1-4 is `[8, 39]`, one contiguous 32-element run skipping only column 0's eight cells, so a term density with no other wide operand packs to one plain `OP_SLICE(offset=8, count=32)`, not a gather. 17 ops to 3 (`CONSTRAIN_LOWER`, `OP_SLICE`, `OP_NORMAL_LPDF`), cheaper than the gather this note originally proposed. **reroll** packs this once `ops_match` accepts an affine family across lanes and the classifier tries the base's storage order before falling back to a lane-major gather.

**Shared vector operand.**

```stan
parameters { vector[K] mu; real<lower=0> s; }
model { for (i in 1:N) y[i, :] ~ normal(mu, s); }
```

(`multi_normal(mu, Sigma)` is out of scope: its kernel is per-row native, and closing it is kernel work, not a lane-classification change.) Today (N=8, K=4, `y` data so each row is `CONST_LANES`): 9 ops, eight separate `OP_NORMAL_LPDF` term densities, each reading a packed constant row and the same invariant `mu[4,P]`. `row_operands_ok` refuses because `mu` is invariant with `len != 1`. Under `LaneLayout`, `mu` is `{lane_stride=0, width=4, invariant=true}`; packing tiles it with `OP_REP_MAT` (mode 1) into one length-32 vector, and the region becomes one `OP_REP_MAT` + one `OP_NORMAL_LPDF` term density over 32 elements. 9 ops to 3. **reroll** packs this too, at the same call site as the partial row: the input classification gains a "wide invariant, tile it" arm beside the existing "scalar invariant, keep it" one.

**Row density feeding an expression.**

```stan
model {
  for (i in 1:N)
    target += log_mix(theta, normal_lpdf(y[i,:] | mu1, s),
                             normal_lpdf(y[i,:] | mu2, s));
}
```

Today (N=8, K=4, `y`/`mu1`/`mu2` data): 25 ops, unrolled verbatim (two `OP_NORMAL_LPDF` plus one `OP_LOG_MIX` per lane). `reroll.cpp:1218` refuses any `elt_density` at `width > 1` outright: `Pos` has no per-lane-reduction tail, so there is nothing to classify into even before the wide-invariant check applies. Under `LaneLayout` each `normal_lpdf` becomes one elementwise density over 32 elements (`OP_REP_MAT`-tiled `mu1`/`mu2`) followed by one `OP_SUM_ROWS(4)`, producing the length-8 per-lane lp vector the existing `term_widen` path for `OP_LOG_MIX` already consumes unchanged. Final shape: 2x(`OP_REP_MAT` + `OP_NORMAL_LPDF` elementwise + `OP_SUM_ROWS`) + one widened `OP_LOG_MIX` + one `OP_SUM_VEC`, 9 ops down from 25. **reroll** packs this, needing the one piece of this design with no direct analog already in `partition.cpp`: reroll has never needed a `Pos::rows` field or its reduction tail before.

## 4. Migration order

Reordered per the amendment below: costing (old step 6) moves ahead of every step that lets reroll fuse a shape it could not reach before.

1. Introduce `LaneLayout` and refactor reroll's row cases onto it: replace `Layout`, `adopt_layout`, `flat_at`, `index_elision`/`row_elision`/`slice_start`/`gather_idx` with layout construction plus the decision from section 2, extracted from `builtin_index_map`'s classifier. This step keeps every existing legality gate unchanged (row 0 start, whole-base coverage, `is_row_read`-only affine matching): the type is new, the set of regions it accepts is not. Every lit case and the harness must stay byte-identical. ~150 lines, low risk: existing tests are the oracle and gate acceptance criteria unchanged.
2. Refactor partition's `indexed_read` onto the same layout and decision, and extend the `w == 1` restriction on `kSlice`/`kElide` to any width once the classifier says contiguous. This is not a pure refactor: it changes which buckets partition's existing cost model accepts, because a wide contiguous read now prices as a slice (`L*W`) instead of a gather (`2*L*W`), and a full-covering one prices as free (elision). The floating-point result of an already-accepted bucket is unchanged (a contiguous gather and a slice read and scatter-add the identical cells, bit for bit); a newly-accepted bucket now sums lanes in the vector kernel's order, the same reassociation class the 10 ULP budget already covers for ordinary term-density fusion. Needs a forward/gradient A/B at recorded points and a new width-`w`-greater-than-1 case for `test_contiguous_bucket`'s family, since the existing scalar case is untouched. `wide_shared` stays until gap 2 closes. ~100 lines, medium risk.
3. Give reroll a cost model before it gains any new fusion ability, mirroring partition's currencies (partition.cpp:894-937) rather than assuming reroll's own dispositions stay free: reroll already emits gathers and tiles constants across wide lanes (reroll.cpp:1007, 1334), so "provably cheap" does not hold once this design's later steps land. Delete the duplicate `kMinLanes` (partition.cpp:50 vs reroll_profile.hpp:12) in the same commit. ~60 lines, low risk in isolation, but it gates every step below.
4. Extend `ops_match`/`op_signature` to accept an affine `idata` family for `OP_GATHER`, not only `OP_INDEX` and today's row ops, so the partial row's per-lane gathers count as one template, and try the base's own storage order (section 3's slice, not a gather) before a lane-major materialization. Closes gap 1, flips `test_row_lanes_bail`'s "uncovered rows not fused" (test_reroll.cpp:1722-1729) to a positive assertion, priced under step 3's model. ~90 lines, medium risk: this class of matcher check has needed a second look before (87ba706f), and needs the same forward/gradient A/B as step 2.
5. Add a "wide invariant, tile via `OP_REP_MAT`" classification arm shared by both passes' input loop, keeping an explicit-index disposition alongside it for lane indices no constant stride expresses (both passes already have one: reroll.cpp:1007-1011, partition.cpp:740-764), and delete `row_operands_ok`'s and `wide_shared`'s blanket rejection of a *mixed* region's `len != 1` invariants (the all-shared, non-mixed case already hoists in both passes, unchanged). Closes gap 2, flips "lane-wide invariant operand not fused" (test_reroll.cpp:1786-1808). Needs the forward/gradient A/B: `OP_REP_MAT`'s backward accumulates in ascending output order (elementwise.cpp:359-364), which is a real reassociation of a shared operand's adjoint, not a storage change. ~80 lines, medium risk.
6. Add `Pos::rows` and an `OP_SUM_ROWS` tail to reroll's `elt_density`, mirroring partition.cpp:1015-1047 including its pricing rule (`elt_costs_per_element`, so a binomial-family density does not regress the way `multi_occupancy` did in partition), and only when the packed operand's flat order actually groups each lane's `width` elements contiguously (repack or refuse otherwise, per the amendment). Closes gap 3. Needs the same A/B, since this replaces a vector density evaluation with a scalar-per-lane one summed afterward, changing kernel instantiation as well as storage. ~100 lines, medium-high risk: new code path, needs the corpus mixture models and fresh gradient checks.

Roughly 580 lines across six commits. Step 1 is a type-introducing refactor with the acceptance set held fixed; step 2 is the first commit that changes behavior, and every commit from there needs the numerical gate the amendment describes, not just steps 1-2.

## Amendments after review

An independent static review of this note against the code found six problems. Corrected inline above; summarized here for anyone who read the original draft.

**Source layout and pack layout are different things, and this note conflated them.** `LaneLayout` as section 2 defines it describes one read's geometry (base, offset, strides): fine for deciding elide/slice/gather. But packing several operands together for one fused op additionally needs them to agree on a *destination* order, and that is not always the source order. `OP_SUM_ROWS` reads contiguous `r*width+k` cells (mixture.cpp:78-89); a lane set packed in column-major source order (`LaneLayout` with `lane_stride=1, elem_stride=count`) sits at `l + count*k`, not `r*width+k`, so a `SUM_ROWS(width)` tail over it sums the wrong cells. The rule: a `LaneLayout` fixes how one operand is *read*; whether that reading order is also usable as the *fused op's* element order depends on what consumes it. A term density with no other wide operand and no reduction tail does not care about order at all (its sum is commutative and every operand broadcasts or aligns element-for-element), so it can take an operand's cheapest source order outright, which is why gap 1's example packs to a plain slice in the base's own column-major order rather than a lane-major gather, corrected in section 3. An `elt_density` with a `SUM_ROWS` tail, or any fusion combining two operands that disagree on order (a natural-order read alongside an `OP_REP_MAT`-tiled operand, which is inherently lane-major), must repack the cheaper side into the order the consumer needs, or refuse the bucket if repacking costs more than the fusion saves. This is real, unresolved algorithm work for gaps 2 and 3 (steps 5 and 6), not a paragraph fix; sections 2-4 are amended to flag it rather than to solve it, since steps 1 and 2 (the only ones implemented under this revision) do not reach it.

**The affine description is not a full replacement; keep the explicit-index case.** Both passes already pack arbitrary, repeated, non-affine lane indices no constant stride expresses, such as `alpha[county_idx[n]]` where `county_idx` repeats (reroll.cpp:1007-1011, partition.cpp:740-764). `LaneLayout` covers the affine family; the explicit per-element index list is a separate, coequal disposition that survives under a new name, not something `base=-1` or any stride trick subsumes. Partition's `kRowSum` (an explicit `sum(vec)` per lane, partition.cpp:827-832) is a third thing again: a computation the source wrote, not a geometry fact, and stays its own disposition.

**Every behavior-changing commit needs a numerical gate, not only the step that closes a gap.** Tiling changes a shared operand's adjoint accumulation order (`OP_REP_MAT`'s backward walks the output ascending, elementwise.cpp:359-364); admitting a previously-declined bucket combines density calls and target sums that were separate; step 6's scalar-then-sum replaces a vector density evaluation outright. Each is real reassociation, priced under the existing 10 ULP budget (OPTIMIZATIONS.md:1145-1149) the corpus and conformance suites already enforce, not a new exemption; each commit updates those records itself rather than deferring to a later step.

**Cost the two new materialization forms before, not after, reroll can reach them.** Old step 6 (a cost model) is now step 3, ahead of the gap-closing steps that would otherwise let reroll fuse an uncosted gather or tile. Section 4 above reflects the reordering.

**The shared classifier is `builtin_index_map`'s, not `try_static_selector`'s.** `builtin_index_map` (builtin_registry.cpp:1247-1355) already classifies a flat offset sequence as contiguous, constant-stride (including stride zero), or irregular (builtin_registry.cpp:1336-1354); that loop is what section 2's decision extracts and reuses. `lower_internal.hpp`'s `StaticSelector` (line 1638) carries only a count and whether an axis dropped; it is a different, much thinner probe used earlier in lowering and cannot report packing geometry at all.

**Six smaller corrections to the audit**, all applied inline above: partition hoists an all-shared, non-term position before its wide-invariant rejection runs, so the rejection (like reroll's) only ever fires on a mixed region, not on every wide invariant; partition's `Emit::kStore` delimits one *element* write, unrelated to reroll's row-store machinery; `OP_REP_MAT`'s two modes take idata `{width, count, 1}` and `{count, width, 2}` respectively; a wide contiguous gather already collapses to one op today, so widening `kSlice`/`kElide` past `w == 1` changes an op's *kind*, not the op *count*, for an already-fusing bucket (`test_contiguous_bucket` tests the scalar case and needs no re-recording; a new width-greater-than-1 case is added instead), and the count only drops for a bucket newly accepted by cheaper pricing or newly elided outright; step 1 keeping `LaneLayout`'s decision byte-identical requires keeping the old legality gates explicitly, not merely trusting the new type, and step 2 is explicitly not a pure refactor; and the item numbers cited in sections 1 and 3 are from `docs/superpowers/plans/2026-09-09-vectorize-consumption-generality.md`, not `OPTIMIZATIONS.md`.

## 5. What to delete, what to refuse

Delete: `adopt_layout` and `flat_at` as free-standing functions, becoming `LaneLayout` construction and a method on it; `row_operands_ok`, folded into the shared decision plus the explicit-index disposition kept per the amendment; `Pos::{index_elision, row_elision, slice_start}`, folded into `LaneLayout`'s elide/slice cases (`gather_idx` stays, renamed, as the explicit-index alternative the amendment requires); `Emit::{kElide, kSlice}` as separate hand-rolled cases in partition, folded into the same shared decision (`kGather` stays as the explicit-index case); the duplicate `kMinLanes`; and reroll.cpp:28-32's header comment describing row lanes as "a SLICE or SLICE_STRIDED reading row `lane`" (it should describe `LaneLayout` instead of two things). The `Layout` enum (`kRows`/`kCols`) does not delete outright: it survives as the two stride conventions `LaneLayout` already carries, so what goes is only the free-standing enum and the separate `adopt_layout` agreement check, not the row-major/column-major distinction itself.

Refuse: a second opcode for tiling (`OP_REP_MAT` already covers both directions); a `multi_normal`/`multi_student_t` row-density generalization here (kernel work, a different design); making partition consume reroll's periodic-template discovery or the reverse (they answer different questions, period versus lane-end, and the recommendation is to share the per-operand description, not the region discovery); folding partition's `kRowSum` (an explicit `sum(vec)` per lane, partition.cpp:827-832) into the density-tail `OP_SUM_ROWS` machinery, since they are different computations that happen to share a kernel, not one disposition; and a cost-model exemption for reroll's existing dispositions on the theory that they were always free, since the review found gathers and wide tiling already in reroll today that this design's own numbers price for the first time.
